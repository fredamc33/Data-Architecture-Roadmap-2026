## Section 8 - Analytics 🚀



### 🔑 Conceptos Clave Dominados:
- **136. Intro: Analytics:** 
- **137. AWS Glue:** servicio que actúa como un "traductor y organizador automático" para conectar, entender y mover datos entre diferentes sistemas de almacenamiento sin que tengas que gestionar servidores. Crea un catálogo centralizado en base a lo que encuentre en S3 (Crawler -> Data Catalog) para luego ser usado por herramientas de análisis (Athena, Redshift o EMR) o visualización (QuickSight). Realiza ETL de forma automática programandolo para el momento en que lo deseas.
Debes diseñar la estructura de tus carpetas en Amazon S3 pensando de antemano en cómo vas a consultar tus datos, ya que el Glue Crawler detectará esa estructura automáticamente para acelerar las búsquedas.
- **138. Glue, Hive, and ETL:** AWS Glue funciona como el mapa o índice central de tus datos (metastore), permitiendo que herramientas de consulta como Apache Hive sepan exactamente dónde y cómo buscar la información. 
AWS Glue ETL es la fábrica inteligente que transforma tus datos brutos en información limpia y estructurada. Lo hace generando código automático (Python/Scala), escalando su potencia (DPUs) según el tamaño del problema, protegiendo los datos con cifrado (en reposo y en tránsito) y avisándote de inmediato si algo sale mal en el proceso (CloudWatch & SNS).
AWS Glue ETL es un sistema sin servidores (Serverless) que limpia y enriquece tus datos antes del análisis, permitiéndote enviarlos a múltiples destinos (como S3, Redshift, JDBC/RDS, Glue Data Catalog) de forma automatizada mediante horarios fijos (Schedulers) o alertas en tiempo real (Triggers), cobrándote estrictamente por el tiempo que toma procesarlos.
El DynamicFrame de AWS Glue es una estructura de datos ultra flexible diseñada para procesos ETL que permite leer, limpiar y transformar colecciones de registros masivos (DynamicRecords) con esquemas inconsistentes o cambiantes sin que el sistema falle, superando las rigideces del Spark DataFrame tradicional.
AWS Glue ETL ofrece un arsenal de transformaciones que van desde limpiezas básicas (borrar nulos, filtrar filas, unir tablas) y conversión a formatos eficientes (CSV, JSON, Avro, Parquet, ORC, XML), hasta algoritmos de Machine Learning (FindMatches) para unificar registros duplicados sin identificadores comunes, permitiendo además la total interoperabilidad con Apache Spark.
ResolveChoice es la herramienta de AWS Glue encargada de solucionar disputas de formato cuando una misma columna recibe tipos de datos mezclados (como texto y números), permitiendo al usuario decidir mediante código o interfaz si desea separar la información en columnas nuevas (make_cols), forzar un tipo de dato único (cast) o estructurarlos para no perder registros (make_struct), o decides ignorar las diferencias numéricas y transformas absolutamente todo a texto plano (String), dejando ambos valores simplemente como letras (project).
- **139. Modifying the Glue Data Catalog from ETL Scripts**: tus propios scripts de código ETL pueden actualizar el Data Catalog sobre la marcha mientras guardan los datos procesados (a parte del comúnmente Crawler - rastreador) -> Agregar nuevas particiones, Actualizar el esquema de la tabla y Crear tablas completamente nuevas. Todo esto siempre y cuando los archivos se guarden en S3.
- **140. Running ETL Jobs with Bookmarks:** operar y automatizar procesos en AWS Glue a través de tres componentes: Schedules (para calendarizar ejecuciones automáticas por tiempo), Job Bookmarks (un mecanismo inteligente que recuerda qué datos ya se procesaron para no duplicar trabajo, procesando solo lo nuevo) y CloudWatch Events (un sistema de alarmas automáticas para reaccionar ante el éxito o fracaso de las tareas disparando correos, servidores u otros flujos de trabajo).
- **141. Glue Costs and Anti-Patterns:** esquema de pago por uso (on-demand) para Procesamiento de datos (Crawlers y ETL), Inventario de datos (Data Catalog) y Entorno de desarrollo (Development Endpoints). No debes usar AWS Glue si no vas a trabajar con Spark. AWS Glue ya es capaz de procesar datos en vivo. Dejó de ser una herramienta exclusiva para tareas nocturnas o por lotes (batch) y pasó a competir en el terreno del tiempo real mediante el uso de Spark Structured Streaming, devorando datos directamente desde herramientas como Kinesis o Kafka.
- **142. AWS Glue Flex Jobs:** opción económica alternativa a la ejecución estándar de AWS Glue. Permite ahorrar hasta un 35% a cambio de tener paciencia, aceptando que tu tarea espere en fila o corra más lento si los servidores de AWS se ocupan con clientes de tarifa completa. Flex no sirve para tareas en vivo, scripts básicos o Inteligencia Artificial. Usa el modo Flex únicamente cuando lo único que te importe sea pagar menos, sin importar el tiempo que tome.
- **143. AWS Glue Studio:** modo visual de trabajar con datos. Te quita la necesidad de programar desde cero al darte una interfaz interactiva para conectar fuentes de datos, transformarlas con un clic, guardarlas ordenadamente y vigilar que todo funcione correctamente desde un solo panel de control. Interfaz Visual de ETL, Orígenes y Destinos, Operaciones de datos (mapear columnas, transformar tipos de datos, unir tablas (joins), tomar muestras (sampling) y particionar los archivos finales) y Panel de Control (Dashboard).
- **144. AWS Glue Data Quality:** capacidad integrada en AWS Glue que permite medir, monitorear y evaluar la calidad de los datos en tus tuberías de ETL (Extract, Transform, Load). Creación de reglas (manual o autogeneradas mediante análisis estadístico) -> Completeness, Uniqueness, etc. Integración nativa -> Job Glue. Lenguaje DQDL (Uses Data Quality Definition Language) -> no solo permite validaciones simples de columnas (como nulos o rangos), sino que soporta evaluación lógica condicional con fallo temprano (fail early), filtros por filas y controles avanzados con CustomSQL y DetectAnomalies. Acciones ante resultados -> fallar/detener el Job si no se cumple un umbral de calidad, o reportar CloudWatch.
- **145. AWS Glue DataBrew:** solución No-Code de AWS para interactuar visualmente con datasets grandes, aplicar más de 250 transformaciones estándar y automatizar el preprocesamiento mediante la creación de Recetas (Recipes) reutilizables en jobs de ETL. 
- **146. AWS Glue DataBrew Demo:**
- **147. Handling PII in DataBrew Transformations:** puedes activar estadísticas de PII (Personally Identifiable Information) dentro de un profile job de DataBrew para que el servicio analice automáticamente el dataset e identifique columnas con datos confidenciales (tarjetas de crédito, DNI/SSN, correos, teléfonos). Luego, puedes aplicar alguna de las sgte técnicas de anonimización y enmascaramiento: Sustitución (REPLACE_WITH_RANDOM...), Mezcla (SHUFFLE_ROWS), Cifrado determinista (DETERMINISTIC_ENCRYPT), Cifrado probabilístico (ENCRYPT), Descifrado (DECRYPT), Eliminación (DELETE), Enmascaramiento parcial (MASK_CUSTOM, _DATE, _DELIMITER, _RANGE) y  Hashing criptográfico (CRYPTOGRAPHIC_HASH).
- **148. AWS Glue Workflows:** herramienta de orquestación nativa en AWS Glue diseñada para coordinar flujos de trabajo ETL complejos. Ideal para pipelines ETL cuyos componentes pertenezcan 100% al ecosistema de Glue. Los Triggers de AWS Glue Workflows son los mecanismos que activan la ejecución de pipelines ETL; pueden funcionar por agenda (cron), manualmente (on-demand), por encadenamiento de tareas completadas o por eventos en tiempo real mediante EventBridge (con opciones de agrupación en batches).
- **149. AWS Lake Formation:** capa de gobernanza, seguridad y control de acceso unificado que se sienta sobre AWS Glue y Amazon S3 para acelerar el despliegue de Data Lakes seguros con permisos granulares a nivel de tabla, columna y fila. En sí el AWS Lake Formation no tiene costo, pero los servicios subyacente a los que se conecta sí se te cobrará (Glue, S3, EMR, Athena, Redshift).
El proceso de construcción de un Data Lake en AWS Lake Formation integra
	1. Crear usuario IAM
	2. Configurar conexión JDBC/Glue -> fuente de datos operacionales
	3. Crear S3 bucket -> capa de almacenamiento
	4. Registrar el S3 path en el lake formation
	5. Crear BD lógica en el catálogo de datos dentro del lake formation
	6. Usar Blueprint (plantilla) para generar un flujo de ingesta
	7. Ejecutar workflow -> ingerir, transformar y catalogar las tablas automáticamente
	8. Otorgar permisos a nivel lake formation a los usuario que consultarán los datos mediante Athena, Redshift Spectrum, EMR, etc.
Para dominar AWS Lake Formation a nivel de arquitectura, es clave recordar que el acceso entre cuentas exige un Data Lake Admin en la cuenta receptora (y AWS RAM si está fuera de la organización), requiere permisos KMS si el catálogo está cifrado y no permite el uso de archivos manifest en Athena o Redshift.
AWS Lake Formation simplifica la seguridad centralizando el control de acceso a través de identidades de IAM/SAML, etiquetas de políticas de datos (LF-TBAC) y reglas de granularidad fina a nivel de base de datos, tabla, columna y fila.
- **150. AWS Lake Formation Data Filters:** permiten definir reglas precisas para restringir filas, ocultar columnas o aislar celdas específicas sobre una tabla, aplicando estas restricciones dinámicamente cuando un usuario ejecuta consultas SELECT mediante la API CreateDataCellsFilter o la consola.
- **151. Amazon Athena:** herramienta serverless para realizar consultas analíticas rápidas con SQL sobre archivos almacenados en Amazon S3, destacando por su compatibilidad con formatos optimizados como Parquet u ORC y su motor basado en Presto.
La integración Athena + Glue representa el pilar analítico serverless más común en AWS: S3 almacena los datos, Glue define y cataloga el esquema, Athena consulta la información con SQL y QuickSight visualiza los resultados en cuadros de mando.
Los Athena Workgroups son la herramienta principal para aislar consultas, gestionar la seguridad con IAM y controlar de forma estricta los costos operativos mediante límites de escaneo de datos por equipo o proyecto.
- **152. Athena and Glue, Costs, and Security:** El modelo de facturación de Amazon Athena se basa estrictamente en el volumen de datos escaneados ($5/TB); por ello, la estrategia fundamental de diseño en ingeniería de datos para maximizar la velocidad y minimizar costos es almacenar la información en S3 usando formatos columnares comprimidos como Parquet u ORC y particionar las tablas.
La seguridad en Amazon Athena integra la autenticación/autorización con IAM y políticas de S3, el cifrado en tránsito mediante TLS, y la protección en reposo sobre el directorio de resultados en S3 a través de modalidades como SSE-S3, SSE-KMS y CSE-KMS.
Los dos antipatrones clave de Amazon Athena que debes recordar para arquitectura y exámenes son no usarlo para visualización o reportes avanzados (usa QuickSight) y no usarlo como motor principal de ETL (usa AWS Glue).
- **153. Athena Performance:** Para lograr la máxima velocidad y el menor costo en Amazon Athena, se deben empaquetar los datos en pocos archivos grandes usando formatos columnares como Parquet u ORC, estructurar carpetas mediante particiones en S3 y sincronizar el catálogo con MSCK REPAIR TABLE cuando se inserten particiones manualmente en S3.
- **154. Athena ACID Transactions:** Las transacciones ACID en Amazon Athena permiten realizar operaciones DML a nivel de fila (UPDATE, DELETE, MERGE) y funciones de Time Travel sobre Amazon S3 mediante Apache Iceberg (o Governed Tables en Lake Formation), requiriendo un mantenimiento periódico de compactación para preservar el rendimiento.
- **155. Apache Iceberg and Athena / EMR / Glue Integration:** Apache Iceberg es un formato abierto de tabla para Data Lakes a escala de petabytes que resuelve los problemas del almacenamiento tradicional en S3, ofreciendo transacciones ACID, actualizaciones/eliminaciones a nivel de fila, particionamiento oculto, evolución de esquema y Time Travel, siendo plenamente compatible con Amazon Athena, EMR, Glue y Spark. 
La arquitectura Iceberg + AWS Glue / S3 utiliza AWS Glue como el catálogo central de metadatos, Amazon S3 como almacenamiento persistente de archivos (generalmente Parquet), y la API de Iceberg para permitir que motores como Spark, Flink y Amazon Athena ejecuten operaciones con transacciones ACID de forma segura y distribuida.
La migración a Apache Iceberg en el Glue Data Catalog habilita transacciones ACID, Time Travel y consistencia en el Data Lake. Se puede ejecutar mediante una migración In-Place (solo se generan metadatos sobre los datos existentes) o mediante una migración Shadow/CTAS (copia y reescritura de datos, ofreciendo mayor validación y un rollback seguro).
- **156. Athena Fine-Grained Access to AWS Glue Data Catalog:** El control de acceso fino en Amazon Athena se logra mapeando cada sentencia SQL a su correspondiente acción de API en AWS Glue dentro de una política de AWS IAM. Para permitir acciones como DROP TABLE, el usuario debe contar explícitamente con el permiso glue:DeleteTable configurado sobre el ARN de la base de datos o tabla en Glue Catalog.
- **157. Apache Spark:** motor estándar para procesamiento analítico masivo en memoria (Batch y Structured Streaming), utilizando una arquitectura Driver-Executor coordinada por un Cluster Manager, optimizado para transformar datos que luego alimentan formatos modernos como Parquet/Iceberg en Amazon S3.
- **158. Athena, Glue, and S3 Data Lakes - Hands On:**
- **159. Athena and CREATE TABLE AS SELECT (CTAS):** La sentencia CTAS (CREATE TABLE AS SELECT) en Amazon Athena es una de las técnicas más eficientes para crear subconjuntos de datos y convertir archivos de S3 a formatos columnares comprimidos como Parquet u ORC, mejorando el rendimiento y reduciendo drásticamente los costos de escaneo SQL.
- **160. Spark Integration with Kinesis and Redshift:** La arquitectura integra Amazon Kinesis para la captura continua de eventos, Spark Structured Streaming para procesar y agrupar streams como tablas dinámicas, y el paquete spark-redshift con Amazon S3 como capa intermedia (staging) para realizar cargas masivas paralelizadas de alto rendimiento sobre Amazon Redshift.
- **161. Spark Integration with Athena:** alternativa serverless para ejecutar cuadernos Jupyter e interactuar con Spark (PySpark/Scala) sin administrar infraestructura. Al apoyarse en Firecracker microVMs, ofrece arranques casi instantáneos y cobra de forma elástica midiendo las DPUs por hora empleadas en el procesamiento.
- **162. Athena Federated Queries:** permite realizar analítica in-situ sobre fuentes de datos heterogéneas (relacionales, NoSQL, logs, Data Warehouses u otros Data Lakes) mediante conectores de AWS Lambda, gestionando credenciales (AWS Secrets Manager) y soportando Passthrough Queries (permite enviar sentencias escritas en el lenguaje nativo del motor de origen, para aprovechar los índices y optimizaciones de la fuente remota) y gobernanza centralizada vía Lake Formation.
- **163. Amazon EMR:** plataforma administrada de Big Data en AWS que ejecuta marcos de trabajo distribuidos del ecosistema Hadoop sobre instancias EC2. Topología de Nodos: Master Node (monitorea la salud global del cluster, 1 única instancia EC2), Core Node (tareas de cómputo + almacena datos en HDFS) y Task Node (solo tareas de procesamiento, ideal para instancias Spot).  Modos de Vida del Cluster: Clusters Transitorios (único uso, luego se destruye todo al terminar) y Clusters de Larga Duración (actua como un motor analítico persistente o Data Warehouse). Ejecución de Trabajos: Selección de parquetes de software, Métodos de conexión (por SSH/Jupyter al nodo Master, o por consola/SDK de AWS) y Steps (procesan datos desde S3 o HDFS -> guarda resultados en S3 u otro almacenamiento persistente).
- **164. EMR, AWS integration, and Storage:** EC2 (Master, Core, Task), VPC (donde se despliegan las instancias), S3 (Data Lake central, almacenamiento persistente), CloudWatch (métricas y alarmas), IAM (acceso) y CloudTrail (auditoría del servicio EMR). Opciones de Almacenamiento en EMR: HDFS (128MB por default, efímero, ideal para caché de resultados intermedios), EMRFS (usar a S3 de forma nativa como si fuera HDFS, almacenamiento persistente, S3 ofrece consistencia fuerte de forma nativa) y Local File System & EBS for HDFS.
- **165. EMR Promises; Intro to Hadoop:** EMR Promises: EMR cobra por hora, si un nodo Core falla se aproviona otro automáticamente, añadir o remover nodos Task en caliente, añadir o remover nodos Core (conlleva riesgo de pérdida de datos al remover si no se desmantelan los bloques de HDFS correctamente). Estrategias de Escalado: EMR Automatic Scaling (Legacy) -> reglas manuales en base a métricas CloudWatch, EMR Managed Scaling (Recomendado) -> ajusta el tamaño automáticamente del cluster en base a la carga, Estrategia Scale-Up -> añadir nodos Core y luego nodos Task hasta el límite definido, Estrategia Scale-Down -> remueve nodos Task y luego nodos Core respetando los límites mínimos. 
Arquitectura Central de Apache Hadoop: MapReduce (reduce resultados intermedios, reemplazado por Apache Spark), YARN (gestión de recursos) y HDFS (para almacenamiento efímero).
- **166. EMR Serverless; EMR on EKS:** EMR Serverless ejecuta aplicaciones analíticas sin necesidad de aprovisionar ni administrar clusters de EC2, escala los workers automáticamente según demanda y los libera al terminar, pero aún es necesario dimensionar adecuadamente la configuración de los workers. 
Ciclo de Vida de la Aplicación: Creating -> Created -> Starting -> Started -> Stopping -> Stopped -> Terminated.
Capacidad Pre-inicializada: mantener workers "calientes" para evitar la latencia de arranque.
Regla del 10%: Spark añade un 10% de overhead a la memoria solicitada para drivers y executors.
Seguridad en EMR Serverless: Reutiliza los esquemas de seguridad estándar de EMR. Cifrado en reposo (SSE-S3 o SSE-KMS) y en tránsito (TLS).
EMR on EKS (Kubernetes-native): Permite enviar jobs de Spark directamente sobre clústeres de Amazon EKS (Elastic Kubernetes Service).
- **167. Amazon Kinesis Data Streams:** Arquitectura -> Producers (envían registros donde cada uno se compone de Partition Key y un Data Blob max 1 MB), Shards (un stream se divide en shards, Partition Key determina a qué shard específico va cada registro) y Consumers (leen y procesan los datos). 
Capacidad por Shard en Escritura (Ingress): 1MB/seg o 1,000 registros/seg por shard.
Capacidad por Shard en Lectura (Egress): Classic Fan-out -> 2 MB/seg compartidos entre todos los consumidores activos del shard. Enhanced Fan-out -> 2 MB/seg dedicados por consumidor por shard.
Retención e Inmutabilidad: Los datos son inmutables. El periodo de retención por defecto es de 24 horas, ampliable hasta 365 días, lo que permite la re-ejecución.
Capacity Modes: Provisioned Mode (saber la cant de shards a priori) y On-Demand Mode (sin gestión ni aprovisionamiento manual de shards).
Mecanismos de Seguridad: Control de Acceso (IAM), En Tránsito (endpoints HTTPS (TLS), En Reposo (KMS y opcionalmente Client-Side Encryption), Aislamiento de Red y Auditoría (VPC Endpoints (PrivateLink) y AWS CloudTrail.
- **168. Amazon Kinesis Data Streams - Producers:** Un Producers se encargan capturar, empaquetar e ingerir datos en tiempo real dentro de las tuberías (shards) del flujo de datos. Transforman eventos del mundo real en registros binarios que se transmiten hacia Kinesis. Existen 3 alternativas principales de productores: AWS SDK (llamadas HTTP directas a la API -> PutRecord y PutRecords. Problema: Hot Shard, para solucionarlo -> resharding (split) o mejorar la cardinalidad de la Partition Key), Kinesis Producer Library - KPL (enviar millones de eventos, Aggregation y Collection, RecordMaxBufferedTime que es tiempo para retiener los datos en memoria local, obliga a usar KCL por el lado del consumidor) y Kinesis Agent (servicio sin código que monitorea e ingiere archivos de logs de forma automatizada).
- **169. Amazon Kinesis Data Streams - Consumers:** Un Consumer se encarga de extraer, procesar y reaccionar a los datos que fueron ingeridos previamente en los shards de un flujo. Existen diferentes alternativas de consumo disponibles: Kinesis Consumer SDK (GetRecords, 5 llamadas GetRecords por segundo por shard), Kinesis Client Library - KCL (para desempaquetar y procesar registros que fueron empaquetados por KPL, usa DynamoDB para guardar el punto de lectura actual y reanudar el procesamiento ante fallos, una fila por cada shard, pero hay que tener cuidado ya que DynamoDB se ralentizará si no se aprovisiona suficiente RCU/WCU, o usar el modo On-Demand; caso contrario daría una excepción ExpiredIteratorException), Kinesis Connector Library & Kinesis Firehose (el 1ero es una librería legacy en Java, basada en KCL, para enviar datos hacia S3, DynamoDB, Redshift u OpenSearch; el 2do es el reemplazo del 1ero, totalmente administrada), AWS Lambda (incluye librerías nativas para des-agregar registros producidos con KPL, permite realizar un proceso ETL ligero, ideal para ejecutar lógica de negocio inmediata) y Librerías de Terceros (3rd Party) (integración con frameworks de Big Data como Apache Spark Streaming, Log4J Appenders, Apache Flume y Kafka Connect).
- **170. Amazon Kinesis Data Streams - Hands On:** 
- **171. Amazon Kinesis Data Streams - Enhanced Fan Out:** resuelve los problemas de ancho de banda y latencia cuando múltiples aplicaciones leen del mismo flujo de datos en tiempo real. Modelo basado en PUSH sobre HTTP/2. La aplicación consumidora llama a la API SubscribeToShard() para registrar una conexión HTTP/2. 2 MB/s por shard DEDICADO a cada consumidor registrado. ~70 ms (entrega inmediata en tiempo real). Hasta 20 consumidores por data stream por defecto. Más costoso.
- **172. Amazon Kinesis Data Streams - Scaling:** Adding Shards (Shard Splitting) -> Divide un shard existente en dos shards hijos independientes, mitigar un Hot Shard, aumenta la capacidad general del stream. Merging Shards -> dos shards adyacentes con poco tráfico en un solo shard hijo, reduce la capacidad total del stream (bajar costos operativos).
Manejo de Orden en los Registros: Se debe leer todo el shard padre antes de comenzar a leer el shard hijo. La Kinesis Client Library (KCL) sirve para este propósito de forma nativa. El Auto Scaling no es una funcionalidad nativa fuera de la caja en el modo aprovisionado de Kinesis.
El resharding no se puede ejecutar en paralelo.
No es posible realizar más de 10 operaciones de escalado en 24 horas por stream, ni tampoco duplicar o reducir a menos de la mitad el número de shards en una sola invocación.
- **173. Amazon Kinesis Data Streams - Handling Duplicates:** Duplicados en el Lado del Productor: Causa Raíz -> productor no tiene respuesta de kinesis tras haber aplicado el PutRecord en el stream, pero que en realidad sí se logro el envío. El productor vuelve a reintentar el envío (Retry PutRecord). Resultado: Kinesis recibe nuevamente los mismos datos. Solución Técnica: Incluir un identificador de registro único dentro del cuerpo o metadatos del dato.
Duplicados en el Lado del Consumidor: Causa Raíz -> Terminación inesperada o caída de un worker, Adición o eliminación de instancias worker, Operaciones de resharding, Redespliegues de la aplicación consumidora. Solución -> Hacer la aplicación consumidora Idempotente (la misma operación, mismo resultado), Manejo de duplicados en el destino final -> operaciones UPSERT en Amazon Redshift/DynamoDB o desduplicación por clave primaria.
- **174. Amazon Kinesis Data Streams - Security:** cinco pilares fundamentales
1. Control de Acceso y Autorización (IAM Policies): limitar qué productores o consumidores pueden escribir o leer de flujos de datos
2. Cifrado en Tránsito (Encryption in Flight): cifrado usando Endpoints HTTPS (TLS/SSL).
3. Cifrado en Reposo (Encryption at Rest): AWS Key Management Service (KMS), AWS Managed Key o administradas por el cliente (CMK - Customer Managed Keys)
4. Cifrado del Lado del Cliente: si se requiere que los datos lleguen ya cifrados antes de ingresar a la infraestructura de AWS, el cifrado debe implementarse manualmente en el código del productor antes de llamar a las APIs de Kinesis. Mayor Complejidad.
5. Aislamiento de Red (VPC Endpoints): conectar servicios de AWS con Kinesis sin exponer el tráfico a la Internet pública (AWS PrivateLink).
- **175. Amazon Data Firehose:** capturar, transformar y cargar automáticamente flujos de datos masivos hacia data lakes, almacenes de datos y herramientas analíticas sin necesidad de gestionar servidores ni escribir código.
1. Fuentes e Ingesta de Datos (Producers): puede recibir eventos (de hasta 1 MB por registro). Servicios de AWS (Kinesis Data Streams, CloudWatch y IoT) y Aplicaciones y Clientes (AWS SDK, Kinesis Agent o clientes web/móviles).
2. Transformación y Conversión de Formatos: Transformación Serverless vía AWS Lambda (convertir CSV a JSON), Conversión de Formato de Almacenamiento (como Apache Parquet u Apache ORC), Compresión Integrada (GZIP, ZIP y SNAPPY -> S3, GZIP -> Redshift).
3. Destinos Soportados (Destinations): escrituras por lotes (batch writes) hacia tres categorías principales de destinos: Destinos AWS (S3, Redshift y OpenSearch), Partners de Terceros (3rd-party) (Datadog, Splunk, New Relic y MongoDB), Destinos Personalizados (cualquier API pública o HTTP Endpoint personalizado).
4. Reglas de Búfer (Buffer Sizing): acumula registros en memoria antes de volcarlos al destino utilizando dos condiciones límite: Buffer Size (activado por tráfico alto - High throughput) y Buffer Time (activado por tráfico bajo - Low throughput). Respaldo en S3.
No soportado: Spark o KCL NO pueden leer directamente de Firehose.
- **176. Kinesis Data Stream Troubleshooting and Performance Tuning:** Producers -> Grandes Productores (agrupar lotes mediante KPL, usar PutRecords) y Pequeños Productores (utilizar lotes con PutRecords o Kinesis Recorder),  Errores 500 o 503 (tasa de error de excepciones en Amazon Kinesis superior al 1%, implementar mecanismos de reintento), Integración con Apache Flink (ajustando RequestTimeout y setQueueLimit en FlinkKinesisProducer), Mitigación de Hot Shards (distribuir uniformemente las cargas seleccionando una clave de partición).

- **184. Amazon OpenSearch Service:** motor de búsqueda, herramienta de análisis y plataforma de visualización de datos. Documentos: unidad básica de búsqueda, consisten en datos estructurados (JSON), posee un ID único. Índices: contenedores lógicos de documentos. El concepto de "Tipos" (Types) ha sido desaprobado y eliminado. Particionamiento (Sharding): un Índice se divide físicamente en múltiples Shards, para escalar horizontalmente, cada shard es en sí mismo un índice completo y autónomo.
- Redundancia y Alta Disponibilidad: Primary Shards y Replicas distribuidos entre nodos, Flujo de Escritura (1ero a Primary Shard luego a las Replicas), Flujo de Lectura (cualquiera, Primary Shard o Replica).
- Dashboards: visualizaciones interactivas como mapas, gráficos circulares, barras de series temporales y métricas de monitoreo continuo.
- Completamente administrado (Fully-managed).
Modelo de Escalamiento y Costos: Escalamiento sin Downtime (no es automático), Pago por uso (horas de instancia, almacenamiento y la transferencia).
- Opciones de Configuración Avanzada del Dominio (Domain Options): Dedicated Master Node(s)(mantener el estado del clúster, rastrear los nodos activos y distribuir los shards), Zone Awareness (distribuir los nodos -> 2 o 3 AZs), Snapshots to S3. 
- Integración Nativa y Aislamiento: Aislamiento de red (Network isolation) (los dominios se despliegan dentro de una VPC privada), AWS Integration (Kinesis Data Streams, DynamoDB Streams, CloudWatch y CloudTrail).
